# Где ASR ломается на казахском

Аудит качества распознавания казахской речи: не «какой WER», а **из чего этот WER состоит**
и насколько ему вообще можно верить на агглютинативном языке с собственной графикой.

## Запуск

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
pip install --index-url https://download.pytorch.org/whl/cpu torch torchcodec

python src/prepare_data.py --minutes 12
python src/transcribe.py --model large-v3 --lang kk --device auto
python src/transcribe.py --model small    --lang kk --device auto
python src/transcribe.py --model large-v3 --lang none --device auto   # без подсказки языка
python src/evaluate.py --hyp results/hyp_large-v3_kk.tsv

# сравнение "студия vs краудсорсинг" на том же прогоне модели
python src/prepare_data.py --source common_voice --out data_cv --minutes 4
python src/transcribe.py --model large-v3 --lang kk --device auto --data data_cv --results results_cv
python src/evaluate.py --hyp results_cv/hyp_large-v3_kk.tsv --data data_cv --results results_cv
```

По умолчанию проект использует локальный кэш в `.hf_cache`, чтобы не зависеть от
`~/.cache/huggingface` и не ломаться в ограниченных средах вроде VS Code / sandboxes.
На macOS и CPU лучше работать через `--device cpu` и `--compute_type int8`, на GPU через
`--device cuda --compute_type int8_float16`.

**macOS: нужен FFmpeg версии 4–8, не последний.** `datasets` декодирует аудио через
`torchcodec`, а тот линкуется на конкретные версии FFmpeg. `brew install ffmpeg`
на 2026 год ставит FFmpeg 9, с которым `torchcodec` падает
(`Library not loaded: @rpath/libavutil.XX.dylib`). Рабочий вариант:
```bash
brew install ffmpeg@7
export DYLD_FALLBACK_LIBRARY_PATH="$(brew --prefix ffmpeg@7)/lib"
```
(добавить экспорт в `~/.zshrc`, чтобы не повторять каждый раз). В Colab эта проблема
не встречалась, системный FFmpeg там уже подходящей версии.

В Colab (T4, бесплатный тариф) прогон 12 минут аудио на `large-v3` в `int8_float16`
занимает порядка 5–8 минут.

## Тесты

Юнит-тесты покрывают чистые функции без сети и аудио: нормализацию/стемминг
(`kk_text.py`) и классификатор ошибок с бутстрапом (`evaluate.py`):

```bash
pip install -r requirements-dev.txt
pytest tests/ -v
```

## Что считаем и зачем

| Метрика | Что делает | Что показывает разница |
|---|---|---|
| `WER_raw` | без нормализации | базовая точка отсчёта |
| `WER_norm` | регистр, пунктуация, дефисы | `raw − norm` = ошибки **метрики**, а не модели |
| `WER_fold` | + ә/ө/ұ/ү/і/ң/қ/ғ → русские аналоги | `norm − fold` = цена **казахской графики** |
| `WER_stem` | + срезание аффиксов | `norm − stem` = цена **морфологии** |
| `CER_norm` | посимвольно | устойчивее WER на агглютинативном языке |

Главный тезис работы: на казахском один неверный аффикс делает всё слово заменой,
поэтому WER систематически завышает деградацию по сравнению с английским.
`WER_stem` и `CER` показывают, сколько смысла модель на самом деле удержала.

`evaluate.py` также считает 95%-й доверительный интервал для `WER_norm` и `WER_stem`
бутстрапом по уттерансам (1000 пересэмплирований). На выборках в десятки записей
он широкий, и без него одно число WER выглядит увереннее, чем есть на самом деле.

## Типология ошибок

Классификатор в `src/evaluate.py::classify` раскладывает каждую замену на:

- спецбуквы (ә/ө/ұ/ү/і/ң/қ/ғ схлопнулись в а/о/у/и/н/к/г)
- аффикс, когда корень совпал, а окончание нет
- спецбуквы + аффикс
- близкая форма, когда фонетически похоже
- уход в русскую графику
- полная замена слова
- пропуск / вставка слова

Плюс отдельно: матрица подмен символов, кандидаты в галлюцинации (гипотеза
аномально длиннее эталона) и распределение автоопределённого языка.

# Отчёт

## 1. Данные

Два источника, оба формально "читаная" речь. Честного стримингового корпуса
спонтанной казахской речи не нашлось (см. `src/prepare_data.py`: issai/Kazakh_Speech_Corpus_2
ближе всего по духу, но лежит одним необработанным tar.gz на 80+ ГБ без разбивки
на уттерансы, для аудита такого масштаба не годится).

| | FLEURS | Common Voice |
|---|---|---|
| Источник | google/fleurs, kk_kz, test | Common Voice kk, test |
| Тип речи | студийная дикторская начитка | краудсорсинг: читают вслух подсказанный текст |
| Условия записи | контролируемые, один диктор на клип | разные микрофоны/устройства/акценты, шум |
| Объём | 43 уттеранса, 12.05 мин | 46 уттерансов, 4.10 мин |
| Модель | `large-v3`, lang=kk, GPU (Colab T4) | `large-v3`, lang=kk, GPU (Colab T4) |

Обе модели одинаковые (`large-v3`), это прямое парное сравнение: разница в
цифрах ниже это конкретно цена условий записи, а не эффект более слабой модели.

## 2. Таблица ошибок

Построчные таблицы для парного прогона `large-v3`/`large-v3` (`results/table_large-v3_kk.tsv`,
`results_cv/table_large-v3_kk.tsv`) появятся в этих папках после того, как скопировать
их из Colab (ячейка 6 в ноутбуке уже это делает, если прогон и сохранение идут в одной
сессии). В репозитории сейчас лежит только агрегированная статистика для этого прогона
(`results*/metrics_large-v3_kk.json`) и построчная таблица со старого локального прогона
на модели `small` (`results_cv/table_small_kk.tsv`), настоящие примеры оттуда:

| reference | hypothesis | WER уттеранса |
|---|---|---|
| қайтқан малға қасқыр өш | қайтыған мауға ғазкүроші | 1.0 |
| адал ұл оздырады жаман ұл тоздырады | әдал өл өздірады жаман өл төздірады | 0.83 |
| ағайынның беті қисық болса да бауыры қисық болмайды | ағайынын беті қисқ болса да бауры қисқ болмайда | 0.63 |

Характерный паттерн видно во втором примере: "оздырады"→"өздірады", модель слышит
слово почти целиком верно, но систематически не туда ставит ә/ө/ұ/ү. Это не
случайный шум, а системная слабость на казахской фонетике.

## 3. Разбор по типам

| Тип | FLEURS (n=43) | Common Voice (n=46) |
|---|---|---|
| близкая форма (фонетика/опечатка) | 59.8% | 60.0% |
| полная замена слова | 13.2% | 15.5% |
| вставка слова | 7.7% | 1.3% |
| пропуск слова | 6.4% | 6.5% |
| аффикс (морфология) | 5.1% | 5.8% |
| спецбуквы (ә/ө/ұ/ү/і/ң/қ/ғ) | 4.3% | 6.5% |
| уход в русскую графику | 2.6% | 1.3% |
| спецбуквы + аффикс | 0.4% | 3.2% |

Раз модель одна и та же, интересен именно этот результат: доля "близкая форма"
почти не поменялась (59.8% против 60.0%), и "пропуск слова" тоже (6.4% против
6.5%). То есть шумные условия записи не меняют характер ошибок модели, они
просто поднимают их общий уровень (см. раздел 4, WER вырос почти в 2 раза).
Заметно выросла категория "спецбуквы + аффикс" (0.4% → 3.2%): в шумной записи
модель чаще путает сразу и графику, и окончание в одном слове, то есть теряет
больше сигнала за раз.

Подмены символов тоже отличаются по характеру. На FLEURS модель чаще всего
теряет букву совсем (`∅→ы`, `ы→∅`, `о→∅`) или заменяет казахскую букву на
русский аналог (`х→қ`, `ң→н`). На Common Voice добавляется третий паттерн:
путаница между самими казахскими буквами (`н→ң`, `ұ→о`, `і→ү`), которого
почти не было на чистой записи. Похоже, что шум не просто "стирает" звук,
а сдвигает его в сторону похожего казахского фонема, не обязательно
русского.

## 4. Насколько цифрам можно верить

Разброс между вариантами WER, сам по себе результат:

|  | FLEURS | Common Voice |
|---|---|---|
| WER_raw | 0.3725 | 0.6128 |
| WER_norm | 0.3055 | 0.5382 |
| WER_fold | 0.2924 | 0.5000 |
| WER_stem | 0.2833 | 0.4896 |
| CER_norm | 0.0617 | 0.1393 |
| delta_normalization | 0.067 | 0.0746 |
| delta_kk_graphemes | 0.0131 | 0.0382 |
| delta_morphology | 0.0222 | 0.0486 |

С одинаковой моделью на обоих источниках, `WER_norm` на Common Voice в 1.76
раза выше, чем на FLEURS (0.54 против 0.31), и это уже не смешано с эффектом
слабой модели: это конкретно цена шумных условий записи. `CER_norm` вырос
даже сильнее, больше чем в 2 раза (0.14 против 0.06), что логично: на
зашумлённой записи страдают отдельные звуки, а не только целые слова.

95%-й доверительный интервал (бутстрап, 1000 пересэмплирований по уттерансам):

- FLEURS: `WER_norm ∈ [0.266, 0.348]`, размах 8 пунктов на 43 записях.
- Common Voice: `WER_norm ∈ [0.475, 0.605]`, размах 13 пунктов на 46 записях.

Даже с этим разбросом интервалы не пересекаются: разница между источниками
реальна, не шум выборки. Но сами интервалы напоминают, что ни 0.31, ни 0.54
не стоит воспринимать как точное число, скорее как диапазон.

Что метрика штрафует несправедливо: WER не различает "модель ошиблась в
одной гласной" и "модель выдала случайное слово", оба считаются одной
заменой. Именно поэтому в проекте четыре WER и отдельная типология: доля
"близкая форма" (раздел 3) показывает, что реальная деградация понимания
смысла заметно меньше, чем говорит голый `WER_raw`.

## 5. Что чинил бы первым за месяц

Порядок, а не список:
1. Нормализатор и морфологически осведомлённая метрика. Без этого не отличить
   прогресс от шума: уже видно на своих данных, что `delta_morphology`
   различается в 2 с лишним раза между источниками, и метрика без этого
   разреза смешала бы domain gap с шумом округления.
2. Целевые данные: код-свитчинг и по-настоящему спонтанная речь, а не ещё один
   читаный корпус. Common Voice здесь только полумера (см. п.1 "Данные"):
   условия записи другие, но текст всё ещё начитанный по подсказке. Отдельная
   задача, найти или собрать размеченные записи естественной казахской речи
   (звонки, интервью, подкасты) с посегментной транскрипцией. issai/Kazakh_Speech_Corpus_2
   выглядит правильным источником по содержанию, но требует отдельной работы
   по сегментации перед тем, как им можно будет пользоваться для аудита.
3. Только потом дообучение, и сначала на паре сотен примеров проверить,
   двигает ли оно `WER_stem`/`CER`, а не только `WER_raw`.

## 6. Тупики и чего не сделал

Технические примечания к этому прогону (не хронология, она в `LOG.md`):

- **Спонтанная казахская речь.** Ни один датасет на HF с streaming-доступом
  не подошёл: issai/Kazakh_Speech_Corpus_2 содержит TV/радио/подкасты (ближе
  всего к спонтанной), но раздаётся одним tar.gz на 80+ ГБ без per-utterance
  разметки. Расфасовать его в `refs.tsv`-формат это отдельная задача, не на
  один день.
- **CUDA/nvrtc в Colab.** `datasets` декодирует аудио через `torchcodec`, а тот
  тянет за собой конкретную CUDA-версию через `torch`. PyPI по умолчанию
  подобрал сборку, которой не хватало `libnvrtc.so.13` в рантайме. Чинится
  установкой `torch`/`torchcodec` из `--index-url .../whl/cpu` (аудио-декод
  это CPU-задача, GPU для распознавания даёт `ctranslate2`, а не `torch`).
- **FFmpeg на macOS.** Тот же `torchcodec` линкуется на FFmpeg конкретных
  версий (4-8), а `brew install ffmpeg` в 2026 году ставит версию 9,
  несовместимую с ним. Решение и команды в README, раздел "Запуск".
- **Сеть до HF в некоторых окружениях.** Загрузка parquet-шарда FLEURS иногда
  падает по таймауту без видимой причины (retry с backoff в `datasets` иногда
  не хватает). В Colab не воспроизводилось, похоже на особенности конкретной сети.
